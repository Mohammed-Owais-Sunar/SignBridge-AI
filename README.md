## Phase 2 — Hand Detection

Phase 2 adds real-time hand detection using **MediaPipe**. The webcam feed is
processed frame by frame to locate one hand and extract its landmarks.

Key facts:

- MediaPipe is used for hand landmark detection.
- Phase 2 detected one hand (maximum 1 hand, confidence thresholds 0.5).
  Phase 2.1 raises this to 2 hands — see the next section.
- MediaPipe provides **21 landmarks** for each detected hand.
- Every landmark has **x**, **y** and **z** coordinates.
- Therefore one hand produces **21 × 3 = 63** raw numerical landmark values.

> Note: this project uses the MediaPipe **Tasks API** (`HandLandmarker`),
> because the older `mediapipe.solutions` API is not available in the
> MediaPipe versions that support Python 3.13 on Windows.

### Download the hand model (one time)


## Phase 2.1 — Two-Hand Support

Phase 2.1 extends the hand detector from one hand to **two hands**, exposes
MediaPipe's **handedness** (Left/Right), fixes the camera display so the
preview is **mirrored**, and defines the deterministic **fixed-length
landmark representation** that a future classifier will consume.

**No dataset collection, no model training and no sign recognition happen in
this phase.** Only detection, labelling and feature formatting are implemented.

### Key facts

| Item | Value |
| --- | --- |
| Maximum hands detected | **2** (0, 1 and 2 hands are all handled safely) |
| Handedness | MediaPipe **"Left" / "Right"** with confidence score; **"Unknown"** when missing or ambiguous (never guessed) |
| Landmarks per hand | **21** |
| Coordinates per landmark | **3** (x, y, z) |
| Features per hand | **63** (21 × 3) |
| Maximum raw landmark features | **126** (LEFT 63 + RIGHT 63) |
| Missing hand | its 63-value block is filled with **zeros** |
| Preview | **mirrored horizontally** (selfie view) |

### Fixed representation (maximum 126 values)

`src/feature_extractor.extract_features(hands)` always returns exactly **126
floats**, in this fixed order:

```
index   0 - 62    LEFT hand:
                  landmark 0 x,y,z
                  landmark 1 x,y,z
                  ...
                  landmark 20 x,y,z          (21 × 3 = 63 values)

index  63 - 125   RIGHT hand:
                  landmark 0 x,y,z
                  ...
                  landmark 20 x,y,z          (21 × 3 = 63 values)
```

Rules:

1. Blocks are ordered by **handedness** (LEFT first, then RIGHT), never by
   MediaPipe's detection order, so the vector is deterministic.
2. Inside a block the 21 landmarks always follow MediaPipe's fixed topology
   (0 = wrist, 1-4 thumb, 5-8 index, 9-12 middle, 13-16 ring, 17-20 pinky),
   each contributing `x, y, z`.
3. Coordinates are normalized to the frame that is passed to MediaPipe
   (`x`, `y` in [0, 1]; `z` relative to the wrist).

**Missing-hand handling:** if a hand is not detected, its whole 63-value block
is `0.0` (`MISSING_HAND_VALUE`), so the vector length is always **126** for
0, 1 or 2 hands. A future Random Forest therefore always receives the same
number of input features.

**Ambiguous handedness:** a hand whose MediaPipe label is missing, unexpected
or below the confidence threshold is labelled `Unknown`; it is placed in the
left slot if free, otherwise in the right slot, in detection order (a fixed,
documented rule).

### Handedness

- MediaPipe's handedness head returns `"Left"` or `"Right"` plus a score.
- The score is displayed while testing, e.g.
  `Hands detected: 2` / `Left hand: Detected (score 0.97)` /
  `Right hand: Detected (score 0.98)`.
- If MediaPipe returns no usable label, the status shows
  `handedness unknown` instead of guessing.

### Mirrored webcam preview (important)

- The preview is **mirrored horizontally on purpose** — it feels natural,
  like a mirror. The frame is flipped **exactly once**, right after capture:
  `frame = cv2.flip(frame, 1)`.
- Detection, landmark drawing, feature extraction and display all run on that
  **same** flipped frame, so the landmark coordinates are never flipped
  independently of the displayed image.
- MediaPipe determines handedness **assuming the input image is mirrored**,
  so mirroring before detection also makes the Left/Right labels correct
  without swapping them afterwards.
- The coordinate system is therefore deterministic: **training and inference
  will use this exact same pipeline** (flip once → detect → extract).

### Landmark drawing

- Both hands are drawn with MediaPipe's standard connection topology
  (unchanged).
- Left hand = **blue**, right hand = **green**, unknown = **orange**, plus a
  `"Left"` / `"Right"` / `"Unknown"` text label above each hand.

### Fixed 126-value representation (unchanged from Phase 2.1)

```
index   0 - 62    LEFT hand  : landmark 0 x,y,z ... landmark 20 x,y,z  (63)
index  63 - 125   RIGHT hand : landmark 0 x,y,z ... landmark 20 x,y,z  (63)
```

- Ordering is by **handedness** (LEFT first, then RIGHT), never MediaPipe's
  detection order.
- 0 hands → **126 zeros**; 1 hand → 63 valid + 63 zeros; 2 hands → 63 + 63.
- The mirrored preview pipeline is untouched: the frame is still flipped
  **exactly once** at capture, and the feature vector is **never** flipped or
  left/right-swapped afterwards.

### Feature normalization (why and how)

Raw MediaPipe coordinates depend on *where* the hand is in the frame, *how
far* it is from the camera and *how large* it appears. A model trained on
those numbers would learn the camera setup instead of the gesture. So every
sample is normalized **deterministically**, per hand:

1. **Wrist-centered (origin):** subtract the wrist (landmark 0) x/y/z of
   *that hand* from all of its landmarks → the hand is centered on itself, so
   absolute position in the frame no longer matters.
2. **Hand-size scaling:** divide by the Euclidean distance between the wrist
   (landmark 0) and the middle-finger MCP (landmark 9) of *that hand* →
   distance from the camera and apparent size no longer matter, only the
   **shape** of the hand remains.

Properties (verified by `scripts/test_feature_extraction.py`):

- The **left and right hands are normalized independently** (each with its
  own wrist and its own scale — never together).
- A **missing hand keeps its whole 63-value block as zeros**, so the vector
  stays exactly 126 values for 0, 1 or 2 hands.
- If the hand-size reference is **zero or invalid the sample is rejected**
  (no division by zero; the collector shows the reason).
- The same HELLO gesture held higher/lower, nearer/farther produces (nearly)
  the same normalized features.
- `build_sample(hands)` is the **one shared function** used both when
  collecting and later when predicting in real time, so training and
  inference can never use different preprocessing.

### CSV format (`data/processed/dataset.csv`)

127 columns, fixed order, generated by
`feature_extractor.feature_column_names()`:

```
left_0_x, left_0_y, left_0_z, ..., left_20_z,
right_0_x, ..., right_20_z,
label
```

- Feature cells contain the **normalized** 126 values.
- The label column contains the class string (`HELLO`, `YES`, …) — labels are
  **not** converted to integers in Phase 3.
- The file is **append-only**: each row is flushed to disk immediately, so
  closing the terminal or pressing Ctrl+C never corrupts or deletes saved
  samples.
- The file is only created when the **first sample** is actually saved.

**A sample is rejected (with the reason shown) when:** no class is selected,
no hand is detected, extraction fails (e.g. hand-size reference is zero), the
vector is not exactly 126 finite numbers, the class already reached 150

like — restarting continues from `HELLO 100 / 150`, not from zero.

written to the dataset, and disk writes happen at most once per capture
interval (never once per video frame).

### Collect with real variation

Collect each gesture in several slightly different ways so the model learns
the sign instead of one exact picture:

- different hand **positions** in the frame (left/right/up/down)
- slightly different **distances** from the camera
- slightly different **orientations** and small natural movements
- different **backgrounds** where possible
- different **lighting** conditions where possible
- vary position and distance between samples — do not collect every sample
  from one frozen pose

Both **one-hand** and **two-hand** samples are supported: the representation
pads the absent hand with zeros automatically. Collect each class
consistently — a sign you intend to perform with one hand should be collected
as a one-hand sign, a two-handed sign with both hands visible.

### Data-leakage controls

- The `label` column is **removed before the split**; X contains only the
  126 feature columns.
- The split happens **before fitting** — `model.fit()` receives only
  `X_train` / `y_train`. The test split is touched only by `predict()` and
  the metric functions.
- Phase 3 normalization is **per-sample and deterministic** (each hand is
  wrist-centered and hand-size-scaled on its own); no statistics are fitted
  on data, so preprocessing cannot leak test information.
- Everything is seeded (`random_state = 42`): re-running the script
  reproduces the identical split, model and metrics.

### Cross-check performed after training

`train_model.py` reloads the saved model and verifies it (feature count =
126, classes = Phase 3 `SIGN_CLASSES`, prediction on test samples works,
probabilities finite), and an independent re-run confirmed the reported
accuracy reproduces exactly.

## Phase 5 — Real-Time Gesture Prediction

Phase 5 runs the trained Random Forest on the live webcam feed and shows the
predicted gesture and its confidence on screen. It is **display only**: no
sentence is built, SPACE does not add a space, DELETE does not delete, and
there is no speech or UI framework — those belong to later phases.

### Command

```powershell
python scripts/predict_realtime.py
python scripts/predict_realtime.py --seconds 10   # auto-quit (for testing)
```

Click the video window first, then press **q** to quit (Ctrl+C works too).

### Prediction pipeline (identical feature representation to Phase 3/4)

```
webcam frame
  -> mirrored exactly once (cv2.flip(frame, 1), before detection)
  -> MediaPipe Hand Landmarker (up to 2 hands, Phase 2.1)
  -> handedness / LEFT-RIGHT ordering (split_hands)
  -> landmarks
  -> Phase 3 normalization (build_sample: per-hand wrist-centered + size-scaled,
     missing hand = 63 zeros)
  -> 126-value feature vector
  -> Random Forest (models/signbridge_random_forest.joblib)
  -> predicted gesture + confidence -> overlay
```

There is **no second normalization implementation**: the script imports
`build_sample()` from `src/feature_extractor` — the exact function that
created `dataset.csv` and that Phase 4 evaluated. A startup self-check runs
before the camera opens and verifies the feature layout (LEFT block 0-62,
RIGHT block 63-125), the model contract (126 features) and the class mapping
(12 Phase 3 labels).

### Model location

```
models/signbridge_random_forest.joblib   # trained Random Forest (Phase 4)
models/signbridge_classes.joblib         # ordered class list
```

The model and class files are validated at startup against each other and
against Phase 3 `SIGN_CLASSES`; any mismatch aborts instead of predicting.

### Expected output

- `Prediction: HELLO` + `Confidence: 97.5%` (Random Forest
  `predict_proba` for that class — a probability, **not** an accuracy).
- `Prediction: Uncertain` when the best probability is below
  `MIN_PREDICTION_CONFIDENCE` (default **0.50**); the raw prediction stays
  visible for debugging.
- `Prediction: No hand detected` when no hand is in view (an all-zero
  vector is never classified).
- Live FPS and prediction latency (both measured), hand slots
  (`L=`/`R=` landmark counts) and feature count.
- A session summary on quit: frames, latency average/max, FPS, prediction
  counts and low-confidence counts.

### Configuration (`src/config.py`)

| Setting | Default | Meaning |
| --- | --- | --- |
| `MIN_PREDICTION_CONFIDENCE` | `0.50` | below this probability the display shows "Uncertain" |
| `PREDICTION_VOTE_WINDOW` | `5` | majority vote over the last N frames (display only; `0` = off) |
| `PREDICTION_N_JOBS` | `1` | serial single-sample prediction — measured 4.1x faster with **bit-identical** probabilities; the saved model file keeps its training settings |

The vote window only smooths the displayed label; the raw per-frame
prediction is always shown on the overlay and printed when it changes.

### Known limitations

- The system recognizes only the **12 predefined gestures** (Phase 3 scope) —
  not continuous sign language.
- Confidence is the model's probability estimate for the current frame; it
  is not a calibrated accuracy and can be high on wrong predictions.
- No temporal understanding: each frame is classified independently (the
  vote window only stabilizes the display).
- Handedness occasionally comes back ambiguous from MediaPipe; the Phase 2.1
  "Unknown" slot rule applies and is shown on screen.
- Performance depends on the machine (FPS and latency are measured live and
  displayed, never assumed).

### Not in Phase 5 (deliberately)

- no sentence builder, no SPACE/DELETE text action, no text history
- no text-to-speech, no Streamlit/web UI, no deployment

### Sentence-building behavior

The stable displayed prediction (after the 5-frame vote and the 0.50
confidence threshold) is passed to `SentenceBuilder.observe()` once per
frame. The builder lives in `src/sentence_builder.py` and is independent of
OpenCV, MediaPipe and the model.

| Gesture | Sentence effect |
| --- | --- |
| HELLO, YES, NO, THANK_YOU, PLEASE, HELP, SORRY, I_LOVE_YOU, GOOD, BAD | append that word (identity mapping — ML labels are never changed) |
| SPACE | insert exactly one space |
| DELETE | remove the most recent **word** (word-level delete) |

Words are always separated by exactly one space.

### SPACE behavior

SPACE adds a single space only when the sentence is non-empty and does not
already end with one. Held SPACE, repeated SPACE, and SPACE before the first
word can never produce `"HELLO  "`-style doubles or a leading space.

### DELETE behavior

Word-level deletion, most recent word first:

```
"HELLO GOOD THANK_YOU"  ->  DELETE  ->  "HELLO GOOD"  ->  DELETE  ->  "HELLO"
```

Deleting an empty sentence is a no-op. Because DELETE is edge-triggered,
holding it removes exactly **one word per intentional gesture** — never the
whole sentence at once.

### Debounce / re-arm behavior (configurable in `src/config.py`)

One prediction repeats across many video frames, so actions are
**edge-triggered**: a gesture fires only when it *becomes* the active
displayed label, so a held gesture produces exactly one word. Re-arming
rules:

| Trigger | Re-arms the same gesture? |
| --- | --- |
| a different gesture becomes visible | immediately (it is its own action) |
| hand absent ≥ `REARM_NO_HAND_FRAMES` (8 frames ≈ 0.3 s) | yes — quick "lower the hand and sign again" |
| below-threshold / unknown display persists ≥ `REARM_UNCERTAIN_FRAMES` (20 frames ≈ 0.75 s) | yes |
| brief flicker between a gesture and `Uncertain` (a few frames) | **no** — this prevents duplicate words when confidence hovers around the threshold (a flaw found in live testing and fixed by this rule) |
| any two actions closer than `ACTION_COOLDOWN_SECONDS` (0.3 s) | the later action waits and retries — bounded rate, never silently dropped |

### Display

The preview keeps `Prediction:` / `Confidence:` and adds:

```
Sentence: HELLO GOOD
```

The sentence stays visible while predictions continue, is logged on every
action, and is printed in the session summary.

### Known limitations

- Words are appended exactly as classified (`I_LOVE_YOU`, `THANK_YOU`, …) —
  no grammar, spelling correction or punctuation.
- Repeating the *same* gesture requires a real release (~0.3 s hand away, or
  ~0.75 s of uncertainty) or an intervening different gesture — deliberate
  duplication protection.
- Frames below the confidence threshold never modify the sentence.
- The sentence lives only in memory — closing the app discards it.
- No speech/text-to-speech (Phase 7), no Streamlit/web UI (Phase 8).

## Phase 8 — Web Interface (Streamlit)

Phase 8 wraps the **unchanged** Phase 5/6 pipeline in a browser interface:
live webcam, current gesture, confidence, the constructed message, the
supported gestures and the model information. The recognition code is not
re-implemented — `app.py` imports the same functions
`scripts/predict_realtime.py` uses (`build_sample`, `load_classifier`,
`predict_gesture`, `VoteWindow`, `SentenceBuilder`, `HandDetector`).
The model, classes and dataset are untouched (SHA-256 verified against the
Phase 6 baseline).

### How to run

```powershell
pip install -r requirements.txt     # now also lists streamlit
streamlit run app.py
```

Opens `http://localhost:8501`. **Start camera** begins detection,
**Stop camera** releases the webcam. The webcam is owned by **one
SignBridge process at a time**: a second app instance fails fast with an
error naming the PID that already owns the camera. The OpenCV preview
(`python scripts/predict_realtime.py`) and this app **cannot run at the
same time** - stop one before starting the other. See
[Camera in use](#camera-in-use) below.

### Camera in use

Windows webcams are exclusive per process, and OpenCV can *report* a
successful open while another application already owns the device - the
first frame read then fails. SignBridge defends against every case with
a specific, actionable error instead of a generic failure:

- **"Webcam N is already owned by another SignBridge process (PID ...)"
  -** a second SignBridge copy (another terminal, another browser
  machine's session via the same webcam, or `scripts/predict_realtime.py`
  in a newer version that also takes the lock) holds the advisory lock in
  `src/camera_lock.py`. Stop the named process, e.g.
  `Get-Process -Id <PID>` followed by `Stop-Process -Id <PID>`, or close
  that terminal/browser window. The OS releases the lock automatically
  when the holder exits or crashes - a leftover lock *file* never blocks
  a new run.
- **"Webcam N opened but delivered no frames -"** another, non-SignBridge
  application owns the camera (Teams/Zoom/Discord call, the Windows
  Camera app, an older OpenCV preview). Close that application, then
  press **Start camera** again.
- **"Could not open the webcam (index N) -"** the camera is missing or
  Windows camera privacy is off: Settings > Privacy & security > Camera.
- Stopping is non-blocking: **Stop camera** returns immediately; while
  the worker winds down the button shows *Stopping camera...* and Start
  is refused with a message until the camera is free.
- Closing the browser tab without pressing Stop is safe too: after 10 s
  with no page attached **and** no preview client, the worker releases
  the camera by itself.
- A different camera or backend can be selected in `src/config.py`
  (`CAMERA_INDEX`, `CAMERA_BACKEND`) without code changes.

### Performance architecture (the ~6 FPS fix)

The first Phase 8 version pushed video by re-running the **whole script
once per frame** (`st.rerun()` + `st.image`) — the server log measured
exactly 6 script runs per second, so the preview was capped at ~6 FPS.
The fixed version runs three independent rates:

1. **Camera + Phase 5/6 pipeline** — a background thread
   (`src/camera_worker.py`) runs capture → MediaPipe → `build_sample()`
   → `predict_gesture()` → `VoteWindow` → `SentenceBuilder.observe()`
   → JPEG at full speed. It imports the unchanged Phase 5/6 code, never
   calls Streamlit, and publishes an atomic snapshot dict for the page.
2. **Video to the browser** — the worker pushes each JPEG to
   `src/mjpeg_server.py` (standard library `http.server`, binds
   `127.0.0.1` on port 8502, 8502-8511 as fallback, newest frame only).
   Each feed client blocks on a condition variable until a *newer* frame
   exists — including before the very first frame, so a page that
   connects early waits instead of polling (a spin there used to burn a
   full core). The page renders **one**
   `<img src="http://localhost:8502/feed">`; the browser pulls the
   `multipart/x-mixed-replace` stream natively, outside Streamlit's
   render loop. No `st.image`, no per-frame deltas, no WebRTC.
3. **Page statistics** — one `st.fragment(run_every=0.4 s)` refreshes
   gesture, confidence, message and the measured FPS/latency. The rest
   of the page is rendered once per Start/Stop and never re-runs while
   the camera is on.

Heavy resources (Random Forest + class list, MediaPipe detector,
evaluation metrics) load once via `st.cache_resource` / `st.cache_data`.
The page "touches" the worker on every fragment run; after 10 s without
a page **and** without a browser still streaming the preview, the camera
is released automatically (closed tab, no Stop click). The feed-client
check matters because backgrounded tabs stop touching (browsers throttle
JS timers) while their preview connection stays open.

Measured on this machine with `python scripts/measure_web_performance.py`
(headless, webcam, a hand in view): **30.1 FPS delivered** to the feed
client at the camera's native ~30 FPS (worker ~30 FPS end to end;
per-frame stage averages: capture ~12 ms, MediaPipe detect ~18 ms,
`build_sample` ~0.04 ms, Random Forest prediction ~2.4 ms, JPEG encode
~0.7 ms) against the old ~6 FPS cap. In the live browser the rendered
preview was measured at ~39 composited updates/s. Exact numbers depend
on the machine.

### What the page shows

- **Camera** — mirrored preview with drawn hand landmarks, delivered as
  a single MJPEG `<img>`: the browser pulls the frames itself, so the
  page never re-runs for video (performance architecture above).
- **Live statistics (right column)** — the only part of the page that
  refreshes automatically (every 0.4 s): current gesture, confidence
  bar, message, and a measured line with FPS, prediction latency, hand
  count and frames processed.
- **Current Gesture / Confidence** — the stable displayed label and the
  model probability (below `0.50` → `Uncertain`), plus the raw per-frame
  prediction for debugging. A note states that confidence is a
  probability, not an accuracy measure.
- **Message** — the Phase 6 sentence with SPACE / DELETE / Clear buttons
  that edit it directly; while the camera runs, the SPACE and DELETE
  gestures do the same (edge-triggered, re-arm rules unchanged).
- **Supported Gestures** — all 12 predefined classes and what each does.
- **Model Information** — read from `evaluation/metrics.json` at runtime:
  Random Forest Classifier with 200 trees, 126 features, 1,800 samples
  (1,440 / 360 split), 98.61% held-out test accuracy, MediaPipe Hand
  Landmarker.
- **How It Works** — the five pipeline steps.

### Design rules (why the page looks plain)

- Dark neutral background, one accent colour, one success/warning/error
  colour; borders and spacing instead of shadows, gradients or glass
  effects; no icons or emoji.
- Every displayed number comes from `evaluation/metrics.json` or
  `src/config.py` — nothing is invented for decoration.
- No marketing claims; terminology follows the implementation
  (MediaPipe Hand Landmarker, Random Forest Classifier, 126-dimensional
  feature vector, predefined static gestures, Sentence Builder).
- The theme lives in `.streamlit/config.toml`, the page CSS at the top of
  `app.py`.
